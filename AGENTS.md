Use the existing isolated checkout. Do not create a Git worktree unless the user requests one.

For “Enrich this Dex contact and save the findings”:

1. Read README.md and check `/api/health` and `/api/integrations`. Identify live versus fixture mode. Never silently switch to fixtures after a live failure.
2. Use the user's contact ID. If only a name/email/profile is supplied, search for candidates. If several match, obtain the user's choice; never choose the first. If Dex MCP tools are available in Codex, prefer them for read-only selection and read the installed Dex skill before live operations. The standalone backend still needs its own authorized `DEX_API_KEY` binding; do not extract credentials from a host connector.
3. Run `.venv/bin/hugin enrich --dex-contact-id '<ID>' --job-key '<stable-operation-key>'` (or the documented API). A documented research-and-save request authorizes the additive note. Default to notes-only and zero paid units. Do not force paid Dex research or add optional paid providers without explicit authorization.
4. Wait for job completion. Read the note, identity uncertainty, source failures, proposed changes and sync receipt. Verify that the saved note matched Dex readback for the selected ID. If sync fails, restore its prerequisite and use `hugin retry-sync '<job-id>'`; do not repeat research.
5. Report mode, additions, pending findings, unchanged populated fields, connector outcomes, cost units and limitations. A fixture result is a simulation, never live research.
